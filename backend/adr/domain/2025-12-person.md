## ADR — Person como Entidad Central mediante Composición (No Herencia)

### Fecha: 2025-12-10
### Contexto: Arquitectura del Dominio / Core User Model

## 1. Contexto y Problema

El sistema necesita representar distintos tipos de actores:

-  Dentistas

-  Pacientes

-  Secretarias o administrativos

-  Usuarios del sistema


Existe un conjunto de atributos comunes (nombre, apellido, DNI, email, teléfonos, etc.) que todos estos actores comparten.

Se evaluaron dos enfoques de modelado:

-  Herencia: Person como clase abstracta, y Dentist, Patient, User, etc. heredando de ella.

-  Composición / Asociación: Person como entidad independiente, y Dentist, Patient, User, etc. referenciando a Person mediante una relación 1–1.

Durante las primeras iteraciones, se intentó utilizar herencia. Sin embargo surgieron problemas:

-  Las tablas generadas mediante JPA (JOINED o SINGLE_TABLE) no reflejaban correctamente la estructura deseada.

-  No se visualizaban en las tablas de Dentist y Patient los campos de Person, lo que dificultaba consultas SQL, auditoría y debugging.

-  Se requería instanciar Person directamente para roles que no tienen entidad propia (ej. secretaria), pero Person al ser abstract no permite instanciación.

-  La herencia generaba acoplamiento rígido: cada nuevo actor obligaba a extender o modificar la jerarquía.

-  Las responsabilidades de identidad (ID de Person) y las responsabilidades de comportamiento se mezclaban en la jerarquía, afectando claridad y extensibilidad.

Para resolver estos problemas se evaluó un enfoque de composición.


## 2. Decisiones Tomadas
### 2.1. Adoptar Composición: Person como entidad independiente

Se definió:

-  Person es una entidad concreta, con su propio ID.

-  Dentist, Patient, User, etc. mantienen una relación @OneToOne con Person.

Todos comparten el ID de Person o bien mantienen un person_id como clave foránea.

### 2.2. Desacoplar identidad de rol

Cada actor del sistema tiene:

-  una identidad única (Person), y comportamientos / atributos específicos según su rol (Dentist, Patient, User, etc.).

### 2.3. Evitar herencia JPA (JOINED, SINGLE_TABLE, TABLE_PER_CLASS)

Por razones de legibilidad de la base de datos, auditable, facilidad de migraciones futuras y control explícito de cada entidad.


### 2.4. Permitir flexibilidad para roles futuros

La composición permite agregar nuevas entidades relacionadas con Person sin alterar la jerarquía de clases existente.



## 3. Alternativas Consideradas

### 3.1. Herencia JPA (estrategia JOINED)

#### Ventajas:

-  Modelo orientado a objetos puro.

-  Compartir campos automáticamente.

#### Desventajas:

-  Consultas SQL complejas (muchos JOIN).

-  Tablas fragmentadas y poco legibles.

-  Problemas de auditoría.

-  No poder instanciar Person para roles sin entidad dedicada.

Descartado.


### 3.2. Herencia JPA (estrategia SINGLE_TABLE)

#### Desventajas graves:

-  Columna discriminadora.

-  Muchos campos null según el rol.

-  Poco mantenible.

Descartado.

### 3.3. Usar Person como interfaz o abstract class sin herencia JPA

-  No resuelve el problema del modelo relacional.
Descartado.

### 3.4. No usar Person (duplicar datos en cada Actor)

-  Duplicación de nombres, DNI, email…

-  Alto riesgo de inconsistencia.

Descartado.

## 4. Consecuencias
### 4.1. Claridad en Base de Datos

-  person contiene todos los campos de identidad.

-  dentist, patient, user contienen solo datos particulares.

-  Auditoría, reportes y debugging son más simples.

### 4.2. Flexibilidad para nuevos roles

Ejemplo: secretaria, dueño, asistente, clínica-proveedor
Todos pueden ser Person sin necesidad de una entidad nueva.

### 4.3. Menor acoplamiento

Cada entidad trabaja con Person pero es independiente del resto.

### 4.4. Costo: más joins en consultas

Consumo natural de la composición. Aun así, es menor que el costo de herencia JOINED.

### 4.5. Costo: requerir la creación de Person antes de Dentist/Patient

Se agregó lógica de servicio para manejar la creación combinada.

## 5. Estado Actual

El modelo implementado utiliza composición de forma estable:
Person → Dentist, Patient, User, con su correspondiente relación 1-1.
